# Что было сделано

Разбор трёх проблем, зафиксированных в [CLAUDE.md](CLAUDE.md): авторизация,
дублирование схемы БД, отсутствие тестов и линтеров.

---

## 1. Авторизация на глобальных эндпоинтах

**Было.** Часть `/api/*` не имела `Depends(get_current_user_id)`. Без всякого токена
можно было удалить любого пользователя (`DELETE /api/users/{id}`), прочитать и снести
VK-интеграцию вместе с access-токеном, выгрузить все посты и аналитику.

**Стало.**

- Токен требуют все `/api/*`, кроме шести явно публичных: четыре auth-ручки,
  `GET /api/invites/{token}` и `GET /api/debug/smtp-test`.
- Одной аутентификации мало — глобальные списки отдавали данные всех групп любому
  залогиненному. Добавлены три хелпера в `utils.py`:
  - `posts_scope` — SQL-фильтр «посты моих групп + мои посты без группы»; подставлен
    в `/api/posts`, `/api/calendar` и все три `/api/analytics/*`;
  - `require_post_access` — доступ к одному посту, с запретом записи волонтёрам;
  - `require_admin` — для ручек вне контекста группы (`/api/users/*`,
    глобальные `settings/vk|telegram`, `posts/sync-vk-stats`).

**Попутно найдено и исправлено:**

| Что | Где |
|---|---|
| `POST /api/posts` брал `author_id` из тела запроса — пост можно было создать от чужого имени | `routers/posts.py` |
| `PUT /api/notifications/{id}/read` не проверял владельца — гасились чужие уведомления | `routers/notifications.py` |
| Рейт-лимит `/api/ai-enhance` считался по IP; за прокси Railway у всех клиентов один IP, то есть 15 запросов в минуту делились на весь сервис. Переключён на `user_id` | `routers/posts.py` |
| `api.uploadFile` слал запрос без заголовка `Authorization` — после включения авторизации загрузка сломалась бы | `frontend/lib/api.ts` |

Легаси-роуты оставлены на месте по решению заказчика: закрыты авторизацией, но не удалены.

## 2. Схема БД: один источник правды

**Было.** Схема описана дважды — в `init_db()` (146 строк `CREATE TABLE IF NOT EXISTS`
и `ALTER TABLE ADD COLUMN IF NOT EXISTS`) и в миграции alembic.

**Что выяснилось при проверке.**

1. **Миграция никогда не работала.** В четырёх вызовах `op.create_foreign_key` вместо
   имён колонок стояло `["groups.id"]` вместо `["id"]` — alembic падал с
   `NoReferencedTableError` на первом же прогоне. Вся схема всегда создавалась `init_db()`.
2. **32 расхождения.** Построил две базы — через `init_db()` и через alembic — и продиффил
   `information_schema`. Пропущенных и лишних колонок нет, но в 32 местах миграция
   объявляла `NOT NULL` там, где реальная база допускает `NULL`. В том числе
   `invite_links.max_uses`, где `NULL` — это рабочая фича (безлимитный инвайт),
   которую `NOT NULL` просто сломал бы.

**Стало.**

- Миграция приведена к реальной схеме (а не наоборот — продовая база уже создана
  `init_db()`). Диff по колонкам и по ограничениям PK/FK/UNIQUE — ноль.
- `init_db()` разделён на `run_migrations()` (`alembic upgrade head`) и `seed_db()`
  (только демо-данные). Весь DDL из кода приложения удалён.
- Существующая продовая база не имеет таблицы `alembic_version`, и `upgrade head`
  на ней пытался бы создать уже существующие таблицы. `run_migrations()` определяет
  такую базу по «`users` есть, `alembic_version` нет» и помечает её `BASELINE_REVISION`
  без DDL. Стампится именно базовая ревизия, а не `head`, — чтобы будущие миграции
  на старой базе применились нормально.
- Из `alembic.ini` убран `sqlalchemy.url` с паролем открытым текстом.

Проверено на живой БД: чистая база, повторный старт (идемпотентность), старая база
без `alembic_version` — данные на месте.

## 3. Тесты и линтеры

**Бэкенд** — `pytest`, **129 тестов**, идут против настоящего PostgreSQL
(база `mediahub_test` пересоздаётся каждый запуск), поэтому SQL в роутерах
проверяется по-честному. Без доступной базы тесты не падают, а пропускаются с подсказкой.

| Файл | Что покрывает |
|---|---|
| `test_auth_required.py` | перебирает **все** роуты приложения и требует зависимость авторизации у каждого, кроме списка публичных; 401 без токена и с мусорным токеном |
| `test_isolation.py` | изоляция между группами: чтение, изменение, удаление, публикация чужого поста; календарь, аналитика, уведомления; подделка `author_id` |
| `test_permissions.py` | админские ручки, запрет удалить/разжаловать самого себя, валидация роли, запрет записи волонтёрам |
| `test_migrations.py` | таблицы созданы миграциями, идемпотентность, стамп старой базы; запрет `CREATE/ALTER TABLE` вне alembic |
| `test_api_behaviour.py` | регистрация, CRUD постов, инвайты, шаблоны, загрузка файлов, аналитика, экспорт xlsx |
| `test_password_reset.py` | полный цикл сброса пароля, рейт-лимит, сокрытие несуществующего адреса |

Два теста работают как «предохранители» от возврата прошлых проблем: перебор роутов
уронит сборку при появлении незакрытого эндпоинта, а проверка на DDL — при возврате
`CREATE TABLE` в код приложения.

**Линтеры.** `ruff` для бэкенда (конфиг в `backend/pyproject.toml`), `eslint` +
`tsc --noEmit` для фронтенда. Исправлен 81 автофикс и 2 замечания вручную; исключения
задокументированы (например, `E402` в `main.py` — роутеры обязаны импортироваться
после `load_dotenv()`).

**Единая точка входа:**

```bash
./check.sh              # ruff + pytest + tsc + eslint
./check.sh backend
./check.sh frontend
```

### Настоящие баги, которые нашли тесты и линтеры

1. **Приём инвайта падал с 500.** В `INSERT INTO group_members` параметры шли в порядке
   `(gid, role, user_id)` вместо `(gid, user_id, role)` — Postgres отвечал
   `invalid input syntax for type integer: "editor"`. Вся схема приглашений в группу
   была нерабочей. — `routers/groups.py`
2. **Сброс пароля падал с 500.** `timedelta` не импортирован, а `datetime` импортирован
   как модуль, поэтому `datetime.utcnow()` тоже неверно. Ломались обе ручки —
   и запрос кода, и смена пароля. — `routers/auth.py`
3. **Нарушение правил хуков React.** `useCallback` вызывался прямо в JSX, то есть после
   раннего `return null`. Между рендерами менялось количество хуков — React падает с
   «Rendered more hooks than during the previous render». — `frontend/app/(app)/layout.tsx`
4. **Расхождение имён полей.** Фронт читал `photo_errors`, бэкенд отдавал
   `vk_photo_errors` — сообщение об ошибке загрузки медиа в VK никогда не показывалось.
   Вскрылось при замене `as any` на нормальный тип `PublishResult`.

## 4. Проверка деплоя на Railway

Изменения затрагивают старт приложения, поэтому отдельно разобрано, что произойдёт
при выкатке. Нашлись два риска, оба закрыты.

### Риск 1: URL-encoded пароль ломал запуск

`alembic.Config.set_main_option()` кладёт значение в ConfigParser, а тот интерполирует
знак «%». Railway отдаёт `DATABASE_URL` с URL-encoded паролем (`%40` вместо `@`), и это:

```
ValueError: invalid interpolation syntax in
'postgresql://user:pa%55wd@host:5432/railway' at position 20
```

Приложение не стартовало бы вообще. Теперь URL идёт мимо ini — через
`config.attributes["db_url"]`, а `env.py` строит движок напрямую через `create_engine`.
Проверено полным прогоном миграций на URL с `%40`. Есть регресс-тест.

### Риск 2: pyproject.toml мог сменить стратегию сборки

Конфиг `pytest` и `ruff` изначально лёг в `backend/pyproject.toml`. Nixpacks определяет
тип Python-проекта по наличию этого файла и мог переключиться с
`pip install -r requirements.txt` на сборку пакета. Конфиги перенесены в
`pytest.ini` и `ruff.toml`, `pyproject.toml` удалён — детект сборки не меняется.

### Предохранитель на «дореформенную» базу

Продовая база создана старым `init_db()` и не имеет `alembic_version`.
Перед тем как пометить её базовой ревизией, `run_migrations()` проверяет, что схема
действительно дотягивает до baseline (16 поздно добавлявшихся таблиц и колонок).
Если чего-то нет — падает с внятным сообщением вместо молчаливого штампа,
который потом дал бы 500-е в рантайме. Есть тест.

### Что проверено дополнительно

| Пункт | Итог |
|---|---|
| `alembic` в `requirements.txt` | есть (`alembic==1.16.5`), SQLAlchemy подтягивается транзитивно |
| Пути к `alembic.ini` и `alembic/` в контейнере | абсолютные, от расположения `main.py` |
| `alembic` из CLI после правки `env.py` | `upgrade head`, `current`, `--sql` — работают |
| `seed_db()` на непустой базе | пропускает вставку, данные не трогает |
| Сборка фронта | `next build` проходит, 20 страниц |

### На что смотреть при выкатке

1. Бэкенд деплоить **первым** — фронт после включения авторизации шлёт токен на `/api/upload`,
   а старый бэкенд его просто проигнорирует; обратный порядок дал бы окно с 401.
2. В логах бэкенда при первом старте должно появиться:
   `alembic: существующая схема помечена ревизией 3ee67a8c2e29`. Строка появляется
   один раз, при последующих рестартах её не будет.
3. Если миграции упадут — приложение не стартует и healthcheck не пройдёт, то есть
   Railway не переключит трафик на сломанный деплой. Прежняя версия продолжит работать.
4. `next build` теперь прогоняет ESLint (раньше конфига не было и шаг пропускался).
   Сейчас предупреждения есть, ошибок нет, сборка проходит. Но учтите: новая
   lint-**ошибка** отныне будет ронять прод-сборку так же, как ошибка типов.
   Отключается одной строкой `eslint: { ignoreDuringBuilds: true }` в `next.config.mjs`.

## Осталось нерешённым

- Миграции запускаются в startup-хуке приложения. При масштабировании больше чем
  в один инстанс правильнее вынести их в отдельную release-команду Railway.
- Загрузки лежат на диске контейнера — на Railway без volume теряются при редеплое.
- Даты в БД хранятся как `TEXT` (`YYYY-MM-DDTHH:MM`). Сортировка работает,
  арифметика по датам и таймзоны — нет.
- `@app.on_event("startup")` устарел, FastAPI просит lifespan-хендлеры.
- Легаси-эндпоинты дублируют групповые: два набора роутов делают одно и то же.
