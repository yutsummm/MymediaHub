# MediaHub

Медиахаб для молодёжных центров (Красноярск): планирование, генерация и публикация
контента в VK и Telegram, аналитика, приём медиа от волонтёров, карта молодёжных центров.

Интерфейс и весь текст — на русском. Пиши сообщения об ошибках и UI-строки по-русски.

## Стек

| Слой | Технологии |
|---|---|
| Backend | Python, FastAPI 0.111, uvicorn, psycopg2 (raw SQL, **без ORM**), pydantic |
| БД | PostgreSQL 16 (локально через docker-compose), alembic для миграций |
| Auth | JWT (python-jose, HS256, 72 ч) + отзываемые сессии в БД, bcrypt |
| Frontend | Next.js 14 App Router, React 18, TypeScript, **CSS без фреймворка** (globals.css) |
| Графики / карты | chart.js + react-chartjs-2, @pbe/react-yandex-maps |
| Внешние сервисы | VK API (5.199), Telegram Bot API, Groq (`llama-3.1-8b-instant`), Brevo/SMTP |
| Деплой | Railway (nixpacks), два сервиса: backend + frontend |

## Ключевые модели данных

`users`, `groups`, `group_members` (роли: `admin` | `editor` | `volunteer`), `invite_links`,
`posts` (status: `draft` | `on_review` | `scheduled` | `published`;
platforms/tags/media — JSON-строки; `submitted_at`/`reviewed_at`/`reviewed_by`/
`review_comment` — согласование),
`templates` (4 сида: announcement, results, vacancy, grant), `notifications`,
`post_stats` (статистика по паре пост+площадка), `publish_jobs` (очередь публикации),
`rate_limits` (счётчики обращений), `sessions` (отзываемые токены),
`vk_settings` / `tg_settings` (с `workspace_id` → groups), `volunteer_media`,
`email_verifications` (заявки на регистрацию до подтверждения почты), `password_resets`.

Даты — `timestamptz` (миграция `f1d4c8b73e29`). JSON-поля — `jsonb` (`e7a2b9f41c58`).

## Архитектурные особенности (важно помнить)

- **Два параллельных набора эндпоинтов**: глобальные (`/api/posts`, `/api/settings/vk`)
  и групповые (`/api/groups/{gid}/posts`, ...). Глобальные — легаси одиночного
  воркспейса, но **не мёртвые**: на них работают пользователи без группы (после
  отмены автовступления это все новички), поэтому удалять их нельзя.
  **Логика у них общая**: `analytics._summary/_timeline/_export` и
  `settings._save_vk/_save_tg/_read_settings/_upsert` принимают область выборки
  (`where`/`params` или `gid=None`), а ручки только её выбирают. Пока это были
  копии, они успели разойтись — глобальное подключение Telegram отвергало
  неверный токен, групповое молча сохраняло. `test_endpoint_parity.py` стережёт,
  чтобы это не повторилось.
- **Посты выходят после согласования — если группа этого требует.**
  `groups.require_approval`: у новых групп включено, у заведённых до миграции
  `c8b3f5d21a70` выключено. Молча включить везде нельзя — там, где единственный
  активный человек редактор, публиковать стало бы некому, и группа встала бы
  без единого сообщения об ошибке. Маршрут: `draft` → `on_review` →
  (`scheduled` | очередь публикации) либо назад в `draft` с замечанием
  (`posts.review_comment`). Логика — в `review.py`, ручки `.../submit`,
  `.../approve`, `.../reject`. **Куда уходит одобренный пост, отдельно не
  хранится**: стоит будущая `scheduled_at` — в расписание, нет — сразу в
  очередь; отдельная колонка «что хотел автор» была бы вторым источником
  правды о том же самом. Проверка `review.check_may_release` стоит на **всех
  трёх** путях выпуска — создание, изменение статуса и ручка публикации:
  `scheduled` подхватит планировщик, так что закрыть одну кнопку мало.
  Администратор группы согласование не проходит — он и есть визирующий.
  `test_post_review.py` стережёт.
- **Медиатека — одно окно на оба источника.** `media_library.browse()`
  объединяет одобренные `volunteer_media` и `posts.media` этой группы,
  схлопывая один и тот же файл в одну карточку (`DISTINCT ON (url)`). Раньше
  выбрать можно было только загрузки волонтёров, да и та кнопка по недосмотру
  проверяла **глобальную** роль `editor`, которой после разделения систем
  ролей не существует, — видели её одни глобальные администраторы. Ссылки
  подписываются на выдаче, как везде. `test_media_library.py` стережёт.
- **Отчёт учредителю — не выгрузка аналитики под другим именем.**
  `GET .../analytics/report`: связный русский текст «что делали и что из этого
  вышло», ключевые показатели, разбивка по направлениям (тегам), по площадкам
  и список публикаций со ссылками на записи ВК. Аналитика в интерфейсе
  отвечает на вопросы того, кто ведёт каналы; этот документ — того, кто их не
  ведёт. **Несобранное пишется словами «нет данных», а не нулём** — и по
  просмотрам, и по реакциям: ноль в отчёте наружу читается как «людям не
  зашло», хотя цифр просто нет.
- **Две системы ролей, и путать их нельзя.**
  `users.role` — про администрирование системы, значения только `admin` | `member`
  (`GLOBAL_ROLES`, миграция `b8e5c9a72f14`, CHECK в схеме).
  `group_members.role` — про работу с контентом, значения `admin` | `editor` |
  `volunteer` (`GROUP_ROLES`, валидируются при смене роли и при выдаче инвайта).
  Раньше наборы совпадали по названиям и означали разное; глобальные `editor`
  и `volunteer` не давали вообще ничего, но по ним рисовалось меню.
  **В интерфейсе право на контент смотрится только по групповой роли**
  (`groupRoles` в сайдбаре, `currentGroup?.role` на страницах), глобальная —
  только для `/users` (`globalRoles`).
- **Рейт-лимит живёт в базе** (`rate_limits`, фиксированное окно). Словарь в
  памяти процесса обнулялся при каждой выкатке и ничего не знал о втором
  инстансе — при двух процессах лимит на подбор пароля фактически удваивался.
  Если база недоступна, счётчик считается в памяти: отказывать людям из-за
  лимитера неправильно. Старые окна чистит `purge_rate_limits()`.
  **Ключ считается по `utils.client_ip()`, а не по `request.client.host`**:
  последний на Railway возвращает адрес их внутреннего прокси, и у каждого
  запроса он свой (`100.64.x`) — из-за этого рейт-лимит на проде не работал
  вовсе. Берём самый правый публичный адрес из `X-Forwarded-For` (подставленное
  клиентом значение остаётся левее настоящего), пропуская `100.64.0.0/10` —
  Python не считает этот диапазон приватным.
- **Миграции — отдельная release-команда, а не startup-хук.**
  `preDeployCommand = "python manage.py migrate"` в `backend/railway.toml`.
  Приложение при старте только проверяет `schema_is_current()` и **отказывается
  подниматься на отставшей схеме** — обслуживать запросы на ней значит выдавать
  500-е пользователям вместо честного отказа. Локально миграции при старте
  включены (`MIGRATE_ON_STARTUP`, по умолчанию 1), на Railway выключены.
  `run_migrations()` в любом случае держит консультативную блокировку
  (`MIGRATION_LOCK_ID`): на Railway новый контейнер поднимается раньше, чем снят
  старый.
- **Списки постраничные.** `paging()` зажимает `limit` в `MAX_PAGE_SIZE` (200),
  `page_meta()` добавляет в ответ `total/limit/offset/has_more`. **Фильтры
  и поиск обязаны быть на сервере** (`q`, `status`, `platform`, `tag`, `date`):
  фильтрация на клиенте поверх страницы даёт «ничего не найдено» вместо
  «нет на этой странице», а `total` должен считаться по тем же фильтрам.
  На фронте — `components/Pagination.tsx`.
- **Поиск по постам — `ILIKE` по триграммным индексам.** Было
  `LOWER(title) LIKE LOWER(%s)`: такому выражению не помогает ни один индекс,
  и каждый ввод буквы в строке поиска означал полный проход по таблице с
  вычитыванием `content` целиком. Теперь `title ILIKE %s OR content ILIKE %s`
  по GIN-индексам `gin_trgm_ops` (миграция `a9d4f1c60b72`); `LOWER(колонка)`
  для такого индекса — уже другое выражение, поэтому именно `ILIKE`.
  Шаблон собирает **только `like_pattern()`**: он экранирует `%`, `_` и `\`,
  иначе запрос «50%» означал «50 и что угодно», а «%» — вообще всё.
  Расширение `pg_trgm` в окружении может отсутствовать: миграция пробует его
  создать под SAVEPOINT и при неудаче пропускает индексы с предупреждением —
  ронять выкатку из-за скорости поиска неправильно. Шаблон короче трёх
  значащих символов триграммами не покрывается и всё равно идёт перебором.
- **Аналитика ходит в базу пропорционально данным, а не длине периода.**
  `_timeline()` раньше выполнял отдельный SELECT на каждый день: неделя — 7,
  месяц — 30, квартал — 90 запросов, и столько же в экспорте. Теперь один
  запрос с `GROUP BY published_at::date`, а дни без постов дорисовываются в
  Python — графику нужен сплошной ряд, и «в этот день ничего не выходило» для
  него не то же самое, что «этого дня нет в ответе». Диапазон сравнивается с
  `published_at` напрямую (а не `published_at::date = ...`), чтобы лечь на
  индекс `ix_posts_published`.
- **Регистрация в два шага.** `POST auth/register` пользователя не создаёт: кладёт
  заявку в `email_verifications` (имя, хеш пароля, код, `invite_token`) и шлёт код
  на почту. Аккаунт появляется только в `POST auth/verify-email`, там же
  применяется приглашение. `auth/resend-code` шлёт код заново. Ссылка-приглашение
  проверяется дважды: на первом шаге `check_invite_usable` (без расхода), на
  втором `redeem_invite` — если за это время ссылку исчерпали, аккаунт всё равно
  создаётся, а в ответе приходит `invite_error`.
- **Секреты в базе зашифрованы.** `vk_settings.access_token` и `tg_settings.bot_token`
  пишутся через `encrypt_secret()` (Fernet, префикс `enc:v1:`), читаются через
  `decrypt_secret()` / `decrypt_row_secret(row, поле)`. Ключ — `TOKEN_ENCRYPTION_KEY`,
  а если он не задан, выводится из `JWT_SECRET` через HKDF: требовать новую
  переменную нельзя, иначе на уже поднятых окружениях шифрование не включится.
  **Смена `JWT_SECRET` без переноса ключа сделает токены нечитаемыми** — интеграции
  придётся переподключить. Значения без префикса читаются как есть (легаси), а
  `encrypt_existing_secrets()` в startup дошифровывает их, идемпотентно.
- **Загрузки отдаются только по подписанной ссылке.** `/uploads/{файл}` требует
  `?exp=<unixtime>&sig=<hmac>`; без подписи — 403, с истёкшей — 410. Подпись
  считается по имени файла и сроку (ключ выводится из `JWT_SECRET`, TTL в
  `UPLOAD_URL_TTL`, по умолчанию 12 ч). Заголовок Authorization к `<img src>` не
  приложить, поэтому право доступа несёт сама ссылка: её выдаёт API тому, кто уже
  видит содержащую запись. Наружу подписывают `row_to_dict` (все посты),
  `volunteer_media` и `POST /api/upload`; **в базу медиа обязано попадать только
  через `media_for_storage()`**, который подпись срезает — иначе в базе осядет
  протухшая ссылка. Имя файла из URL берётся через `upload_filename()`, а не
  `os.path.basename` (тот утащит и query).
- **Статистика — по площадкам, отдельно.** Таблица `post_stats` с ключом
  (`post_id`, `platform`); `posts.views/reactions/comments/shares` **удалены**
  (миграция `f4b2e8c15d93`). NULL в счётчике = «не собирали», ноль = «собрали, там
  ноль» — на этой разнице держится честное «нет данных». Пишет только
  `stats.save_platform_stats()`, он же не затирает прежнее значение переданным None.
  Наружу посты идут через `stats.serialize_post/serialize_posts`: поля
  `views/...` — сумма по площадкам, плюс разбивка в `stats`. Аналитика берёт суммы
  из представления `post_totals`, разбивку — через `_platform_stats()`;
  `stats_available` теперь считается по данным, а не по списку площадок.
- **Производные показатели существуют не всегда.** `engagement_rate` и `avg_views`
  отдаются `null`, если просмотры не собирали. Раньше знаменатель страховали
  через `max(views, 1)`: ноль просмотров и три реакции превращались в 300 %,
  а ноль и ноль — в ровные «0,0 %», неотличимые от честного «людям не заходит».
  Различить помогает `post_totals.*_samples` (миграция `b2e6a3d95f41`) — `COUNT`
  по ненулевым значениям: суммы в представлении обёрнуты в `COALESCE(...,0)` и
  сами по себе «не собирали» от «собрали ноль» не отличают. Сами суммы (
  `total_views` и соседи) остались числами — на них завязаны сортировка топа и
  выдача наружу. Считают `_engagement()` / `_avg_views()` / `_collected_views()`;
  в xlsx на месте `null` пишется «нет данных», на фронте — прочерк.
- **Статистика Telegram — только реакции и только вперёд.** `telegram_stats.py`,
  отдельный такт планировщика (`TELEGRAM_POLL_SECONDS`, 300).
  **Просмотры Bot API не отдаёт ни одним методом** — нужен MTProto с авторизацией
  живым аккаунтом, поэтому по просмотрам остаётся «нет данных».
  Реакции нельзя запросить для старого поста: Telegram шлёт `message_reaction_count`
  как входящий апдейт, поэтому их вычитывают из `getUpdates` и копят, а смещение
  хранится в `tg_settings.updates_offset`. Бот обязан быть админом канала.
  Выключается через `TELEGRAM_STATS_ENABLED=0`.
- **Глобальные админы.** Роль `users.role='admin'` меняет только другой админ, а
  регистрация всем ставит `editor`. Страница `/users` (только для админов) это
  делает; `ensure_admin_exists()` при старте предупреждает, если не осталось
  админа, способного войти, а `BOOTSTRAP_ADMIN_EMAIL` разово поднимает указанного
  пользователя до админа — иначе выбраться из запертого состояния было бы нечем.
- **Публикация асинхронная, через очередь.** `POST .../publish` только ставит
  задачу в `publish_jobs` и сразу отвечает; отправкой занимается фоновый воркер
  (`publish_queue.process_jobs`, такт `PUBLISH_POLL_SECONDS`, 3 с). Раньше
  загрузка видео в ВК (таймаут 120 с на файл) шла прямо внутри HTTP-запроса и
  упиралась в таймаут прокси, причём отвалившийся запрос ничего не отменял.
  Состояние — `GET /api/publish-jobs/{id}` и `GET /api/posts/{id}/publish-job`;
  на фронте `waitForPublish()` опрашивает задачу. Один пост не может стоять в
  очереди дважды (частичный уникальный индекс `uq_publish_jobs_active`).
  **Повторов при ошибке нет** — публикация не идемпотентна; прерванные задачи
  помечает `requeue_stuck_jobs()` при старте. Планировщик отложенных постов
  тоже ставит в очередь, а не публикует сам.
- **Публикация — одна функция на всех.** `publishing.perform_publish(conn, post, group_id)`;
  `group_id=None` — легаси-настройки одиночного воркспейса (строка с `id=1`).
  Её зовут обе ручки публикации и планировщик; копий больше нет.
- **Планировщик отложенных постов** — `scheduler.py`, фоновая asyncio-задача внутри
  приложения (отдельный воркер избыточен: том Railway и так держит один инстанс).
  Раз в `SCHEDULER_INTERVAL_SECONDS` (60) забирает созревшие посты.
  Заявка на публикацию — `posts.publish_attempts`: берутся только посты с нулём
  попыток, счётчик растёт тем же запросом. Блокировки строки мало: она снимается
  на коммите, а статус до публикации остаётся `scheduled`. **Повторов нет
  сознательно** — публикация не идемпотентна, повтор после таймаута даст вторую
  запись на стене. Оборвавшиеся посты подсвечивает `flag_interrupted_posts()`.
  Просроченные больше чем на `SCHEDULER_MAX_DELAY_MINUTES` (120) не публикуются
  вовсе — `flag_missed_posts()` пишет причину в `posts.publish_error`.
  Выключается через `SCHEDULER_ENABLED=0`.
- **Даты — `timestamptz`, а не текст.** Раньше все «временные» поля лежали в TEXT
  «YYYY-MM-DDTHH:MM»: ни зоны, ни арифметики, фильтры собирались строковыми
  сравнениями (`published_at LIKE '2026-08-16%'`). Работало это только потому, что
  лексикографический порядок такого формата совпадает с хронологическим.
  Теперь в базе абсолютный момент, а зона применяется **только на выдаче**:
  `row_to_dict` прогоняет `DATE_FIELDS` через `fmt_dt()` и отдаёт прежний формат —
  договор с интерфейсом не менялся. Входящие даты читает `parse_dt()`: строка без
  зоны означает местное время (его человек видит в браузере).
  В коде «сейчас» — только `app_now()` (`APP_TZ`, по умолчанию `Asia/Krasnoyarsk`).
  Расхождение зон теперь структурно невозможно; `check_time_alignment()` при старте
  сверяет уже не зоны, а сами часы приложения и базы.
  **Сессия Postgres тоже открывается в `APP_TZ`** (`utils._session_options()`,
  параметр подключения — лишнего запроса нет). От зоны сессии зависят выражения
  вида `published_at::date`, а без явной установки Postgres берёт зону сервера:
  на Railway это UTC, и «день» в аналитике и в фильтре постов по дате
  заканчивался бы в 17:00 по Красноярску. Незнакомое значение `APP_TZ`
  подключение не роняет — параметр просто не подставляется.
- **JSON-поля — `jsonb`.** `platforms`, `tags`, `media`, `tg_message_ids`,
  `templates.fields`. Раньше это был TEXT: приложение само делало `json.dumps` /
  `json.loads`, а фильтры выглядели как `platforms LIKE '%"vk"%'` — такой шаблон
  нельзя проиндексировать и он совпадает с подстрокой внутри чужого значения
  (тег `vk-новости` находился по фильтру `vk`). Теперь `platforms ? 'vk'` и
  `tg_message_ids @> '[123]'` по GIN-индексам. На запись — `psycopg2.extras.Json`,
  на чтение psycopg2 отдаёт готовые списки (`as_json_list` страхует от мусора).
- **Токен отзываемый.** У каждого JWT есть `jti`, которому соответствует строка
  в `sessions`; `get_current_user_id` проверяет её на каждом запросе (точечный
  поиск по первичному ключу). Раньше отозвать токен было нельзя ничем: выход
  жил только на клиенте, а сам токен работал до 72 часов.
  `POST auth/logout` гасит текущий токен, `auth/logout-all` — все остальные,
  `GET auth/sessions` показывает активные входы. **Смена пароля гасит все
  сессии** (`revoke_user_sessions`) — иначе сброс пароля не мешал тому, кто увёл
  токен. Токены без `jti` (выданные до появления сессий) не принимаются.
  Просроченные чистит `purge_sessions()`.
- **Логи — `logging`, а не `print`.** `logs.py`: уровни, JSON на Railway
  (`LOG_FORMAT`, по умолчанию json при `RAILWAY_ENVIRONMENT`) и человекочитаемый
  формат локально. У каждого запроса есть идентификатор: он в заголовке
  `X-Request-Id`, в каждой записи лога и в теле пятисотки — по нему запись
  находится точным поиском, и человеку есть что назвать в обращении.
  Непойманные ошибки ловит `@app.exception_handler(Exception)`: трейсбек уходит
  в лог, наружу — только идентификатор. Идентификатор пользователя проставляет
  разбор токена **двумя путями сразу**: в контекстную переменную (её видят
  записи самого обработчика) и в `request.state` — синхронные обработчики
  FastAPI выполняет в отдельном потоке, и обратно в middleware изменение
  контекста не возвращается.
  **`alembic/env.py` больше не зовёт `fileConfig`**: тот по умолчанию выключает
  все ранее созданные логгеры и переставляет уровень корневого, а миграции
  катятся из startup-хука — приложение после старта замолкало целиком.
  `test_logging.py::test_migrations_do_not_silence_the_app` стережёт.
- **Состояние — `GET /api/health`**, без авторизации (мониторинг ходит без
  токена), наружу только флаги и счётчики. 200 — всё в порядке, 503 — нет.
  Внутри: база, свежесть схемы, длина очереди публикации, просроченные посты и
  **пульс фоновых циклов** (`health.HEARTBEATS`, отмечается только после
  успешного такта). Смерть планировщика иначе снаружи не видна вообще:
  отложенные посты просто перестают выходить.
- **Удаление: смета, подтверждение, след.** Правила внешних ключей разведены по
  смыслу (миграция `e3b7d2f81a45`): содержимое группы уходит вместе с ней
  (`posts`, `notifications`, `vk_settings`, `tg_settings` — CASCADE), следы
  человека остаются без автора (`posts.author_id`, `groups.created_by`,
  `invite_links.created_by` — SET NULL). До этого правила стояли случайно:
  участников и приглашения сносил CASCADE, а посты и интеграции внешние ключи
  не пускали вовсе — **группу хотя бы с одним постом удалить было физически
  нельзя**, запрос падал с ForeignKeyViolation и отдавал 500. То же с
  пользователем, написавшим хоть один пост.
  `DELETE /api/groups/{gid}` требует `?confirm=<точное название>`,
  `DELETE /api/users/{id}` — `?confirm=<точная почта>`; без совпадения 409 со
  сметой. Смету считает сервер (`audit.group_deletion_preview` /
  `user_deletion_preview`), ручки `.../deletion-preview`.
  Всё необратимое пишется в `audit_log` (`audit.record`, **в той же
  транзакции**, что и само действие): удаление группы/поста/пользователя/медиа,
  снятие участника, смена роли, отзыв приглашения, отключение интеграции.
  Читается через `GET /api/audit` (глобальный админ) и
  `GET /api/groups/{gid}/audit` (админ группы). `audit_log.group_id` намеренно
  **без внешнего ключа** — запись обязана пережить удалённую группу.
- **Авторизация**: все `/api/*` требуют `Depends(get_current_user_id)` (или
  `current_session` — то же самое плюс `jti` для ручек выхода), кроме
  `auth/login`, `auth/register`, `auth/verify-email`, `auth/resend-code`,
  `auth/forgot-password`, `auth/reset-password`,
  `GET /api/invites/{token}`, `GET /api/health`. Групповые роуты проверяют
  членство через `require_group_member`. Глобальные списки постов/аналитики
  фильтруются хелпером `posts_scope` (посты групп пользователя + его посты без группы),
  одиночные операции — через `require_post_access`. Ручки вне контекста группы
  (`/api/users`, глобальные `settings/*`, `posts/sync-vk-stats`) закрыты `require_admin`
  (глобальная роль `users.role == 'admin'`).
- **Деплой.** Два сервиса Railway, nixpacks. Бэкенд катить первым (фронт шлёт токен
  на `/api/upload`). URL базы передаётся в alembic через `config.attributes`, а не через
  `alembic.ini` — ConfigParser интерполирует «%», а Railway отдаёт URL-encoded пароль.
  Конфиги `pytest`/`ruff`/`mypy` лежат в `pytest.ini`, `ruff.toml` и `mypy.ini`, а **не** в `pyproject.toml`:
  его наличие меняет детект сборки в nixpacks.
- **Схема БД — только alembic.** При старте `run_migrations()` в [main.py](backend/main.py#L69)
  делает `alembic upgrade head`, затем `seed_db()` заливает демо-данные (идемпотентно,
  по `COUNT(*) == 0`). CREATE TABLE в коде приложения быть не должно — новая колонка
  заводится через `alembic revision`. Автогенерация недоступна (ORM нет, `target_metadata=None`),
  миграции пишутся руками через `op.*`.
  База, созданная старым `init_db()` до перехода, распознаётся по отсутствию
  `alembic_version` и помечается `BASELINE_REVISION` без повторного DDL.
- Прокси API: фронт ходит на относительные `/api/*`, next.config.mjs делает rewrite на
  `BACKEND_URL` (прод-фолбэк: `backend-production-30d6.up.railway.app`).
- Загрузки лежат в каталоге `UPLOAD_DIR` (по умолчанию `backend/uploads/`). На Railway
  к сервису Backend примонтирован том в `/data`, а `UPLOAD_DIR=/data/uploads` — без
  этого диск контейнера пересоздаётся при выкатке и все файлы пропадают.
  `check_upload_storage()` при старте проверяет запись и пишет в лог, где реально
  лежат загрузки; если путь дефолтный, ругается предупреждением.

## Проверки

```bash
./check.sh              # всё: ruff + mypy + pytest + tsc + eslint
./check.sh backend      # только бэкенд
./check.sh frontend     # только фронтенд
```

- **Бэкенд**: `ruff` (конфиг в [backend/ruff.toml](backend/ruff.toml)), `mypy`
  ([backend/mypy.ini](backend/mypy.ini)) и `pytest`.
  Строгость mypy умеренная и выбрана по делу: `check_untyped_defs` (без него
  половина роутеров не проверялась бы вовсе) ловит ровно тот класс ошибок, на
  котором проект уже спотыкался — перепутанные типы аргументов и обращение к
  результату `fetchone()`, который может оказаться `None`.
  `implicit_optional = True` — вынужденно: `request: Request = None` это идиома
  FastAPI, с аннотацией `Request | None` фреймворк принимает параметр за поле
  pydantic и падает при старте.

  Тесты идут против **настоящего PostgreSQL** (база `mediahub_test` пересоздаётся каждый
  запуск, адрес переопределяется через `TEST_DATABASE_URL`) — SQL в роутерах проверяется
  по-честному. Без запущенной базы тесты не падают, а скипаются с подсказкой.

**Про ORM — решение осознанное.** Переводить проект на SQLAlchemy ORM не стали:
слой данных держится на вещах, которые ORM выражает плохо или никак —
`FOR UPDATE SKIP LOCKED`, `pg_advisory_lock`, частичные уникальные индексы,
`ON CONFLICT DO UPDATE`, jsonb-операторы `?` и `@>`, представление `post_totals`.
Плюс схема уже имеет единственный источник правды — миграции alembic; модели
ORM завели бы второе описание той же схемы, то есть ровно проблему №2, которую
закрыли раньше. Оба бага, которые приписывались «сырому SQL», лечатся дешевле:
перепутанные параметры — именованными параметрами (`%(name)s`, psycopg2 умеет
это из коробки), а `datetime` вместо `timedelta` — проверкой типов.

Осталось нерешённым:

- Планировщик и воркер публикации запускаются в startup-хуке приложения. К нескольким
  инстансам они готовы (заявки через `publish_attempts` и `FOR UPDATE SKIP LOCKED`),
  но каждый инстанс будет держать свою копию цикла — при росте нагрузки их лучше
  вынести в отдельный сервис Railway.
- Загрузки лежат на диске контейнера — на Railway без volume теряются при редеплое.
- `@app.on_event("startup")` устарел, FastAPI просит lifespan-хендлеры.
- Соединение с базой в роутерах закрывается вручную. На ожидаемых путях везде
  есть `conn.close()`, но при неожиданном исключении соединение остаётся
  открытым до сборки мусора: 42 вызова `get_db()` не обёрнуты в try/finally.
  Лечится контекстным менеджером, но это правка во всех роутерах разом —
  делать её вместе с чем-то ещё не стоит.

## Даты в БД

Все «временные» поля — `timestamptz` (миграция `f1d4c8b73e29`). В базе лежит
абсолютный момент, часовой пояс применяется только на границе с интерфейсом.

- **Наружу**: `row_to_dict` прогоняет `DATE_FIELDS` через `fmt_dt()` и отдаёт
  прежний формат `YYYY-MM-DDTHH:MM` в `APP_TZ`. Формат хранения поменялся,
  договор с интерфейсом — нет.
- **Внутрь**: `parse_dt()`. Строка без зоны означает **местное** время: именно
  его человек вводит в браузере. Строка с зоной берётся как есть.
- **«Сейчас»**: только `app_now()`. `datetime.now()` на Railway вернёт UTC.
- В SQL теперь можно нормально: `created_at > NOW() - INTERVAL '30 days'`,
  `published_at::date = %s::date`. Строковые `LIKE 'YYYY-MM-DD%'` не нужны.

`invite_links.expires_at`, `password_resets.expires_at` и
`email_verifications.expires_at` тоже стали `timestamptz`; код сравнивает их
с `datetime.now(timezone.utc)` — наивных дат в проекте больше нет.
