# Развёртывание медиаПространства на своём сервере

Инструкция для Ubuntu 22.04 или 24.04. Рассчитана на один сервер: база,
API и веб-интерфейс на одной машине.

Если всё под рукой — домен, сервер и ключи, — установка занимает около часа.
Больше половины этого времени уходит не на команды, а на получение доступов к
внешним сервисам.

---

## 1. Что получится

Три процесса и веб-сервер перед ними:

```
        интернет
           │  https
           ▼
      ┌─────────┐
      │  nginx  │  сертификат, домен
      └────┬────┘
           │
     ┌─────┴─────────────────┐
     ▼                       ▼
┌──────────┐          ┌─────────────┐
│ Next.js  │          │  FastAPI    │  /api/*, /uploads/*
│  :3000   │          │   :8000     │
└──────────┘          └──────┬──────┘
                             │
                      ┌──────┴──────┐
                      │ PostgreSQL  │
                      └─────────────┘
```

Внутри API дополнительно крутятся четыре фоновых цикла: публикация отложенных
постов, разбор очереди отправки, автоснятие и сбор реакций Telegram. Отдельных
процессов для них не нужно — они живут внутри приложения.

**Почему без Docker.** На одной машине контейнеры добавляют слой, который надо
понимать при каждой поломке, и ничего не дают взамен: зависимостей мало,
собирать нечего. systemd проще объяснить тому, кто будет это обслуживать
после вас.

## 2. Что нужно заранее

### Сервер

| | |
|---|---|
| ОС | Ubuntu 22.04 LTS или 24.04 LTS |
| Память | 4 ГБ (на 2 ГБ соберётся, но впритык — сборка интерфейса прожорлива) |
| Диск | 20 ГБ на систему плюс запас под загрузки |
| Доступ | root или sudo по SSH |

Про диск стоит подумать заранее: фото и видео с мероприятий копятся быстрее,
чем кажется. Сто постов с несколькими снимками каждый — это уже гигабайты.

### Домен

Нужен и должен указывать на сервер **до** начала установки: без него не
выпустить сертификат.

**HTTPS обязателен.** Через систему ходят пароли и токены доступа, а браузер
забирает загруженные файлы по подписанным ссылкам. Без сертификата это всё
поедет открытым текстом.

А вот распространённое опасение можно снять: **соцсети к вашему серверу не
обращаются.** И ВКонтакте, и Telegram получают фотографии и видео загрузкой,
байтами — им неоткуда узнать ваш адрес и незачем к нему ходить. Сервер может
стоять хоть за NAT.

### Внешние сервисы

| Сервис | Зачем | Обязателен |
|---|---|---|
| **Brevo** или свой SMTP | письма с кодом подтверждения | **Да** |
| Яндекс.Карты | карта центров, выбор места события | Нет |
| Groq | генерация текстов по шаблонам | Нет |
| ВКонтакте | токен сообщества | Подключается позже, из интерфейса |
| Telegram | токен бота | Подключается позже, из интерфейса |

Про почту отдельно: **без неё нельзя зарегистрироваться вообще.** Регистрация
идёт в два шага, и аккаунт создаётся только после ввода кода из письма.
Заводить пользователей в обход этого пришлось бы прямо в базе.

Ключи Яндекс.Карт и Groq выдаются бесплатно и берутся за пять минут:
[Кабинет разработчика Яндекса](https://developer.tech.yandex.ru/services/),
[console.groq.com/keys](https://console.groq.com/keys).

## 3. Установка

### Шаг 1. Забрать код

```bash
sudo mkdir -p /srv/mediahub
sudo git clone https://github.com/yutsummm/MymediaHub.git /srv/mediahub
cd /srv/mediahub
```

### Шаг 2. Прогнать установочный скрипт

```bash
sudo bash deploy/install.sh
```

Он ставит пакеты (Python, Node.js 20, PostgreSQL, nginx), заводит системного
пользователя `mediahub`, создаёт каталоги, базу и роль, ставит зависимости.

Запускать повторно безопасно: то, что уже сделано, пропускается.

В конце скрипт напечатает **сгенерированные секреты** — `JWT_SECRET`,
`TOKEN_ENCRYPTION_KEY` и строку подключения к базе с паролем. Скопируйте их
сразу: пароль базы больше нигде не сохраняется.

### Шаг 3. Заполнить настройки бэкенда

```bash
sudo -u mediahub cp backend/.env.example backend/.env
sudo -u mediahub nano backend/.env
```

Обязательный минимум:

```ini
DATABASE_URL=postgresql://mediahub:ПАРОЛЬ_ИЗ_ШАГА_2@localhost:5432/mediahub
JWT_SECRET=...из шага 2...
TOKEN_ENCRYPTION_KEY=...из шага 2...
BACKEND_URL=https://ваш.домен
ALLOWED_ORIGINS=https://ваш.домен
UPLOAD_DIR=/var/lib/mediahub/uploads
APP_TZ=Asia/Krasnoyarsk
MIGRATE_ON_STARTUP=0
BREVO_API_KEY=...
BREVO_SENDER_EMAIL=noreply@ваш.домен
```

Три вещи, на которых чаще всего спотыкаются:

**`JWT_SECRET` задать один раз и не менять.** При смене слетают все входы. И,
что важнее, из него выводится ключ шифрования токенов соцсетей — поэтому
`TOKEN_ENCRYPTION_KEY` лучше задать отдельно, тогда эти две вещи развязаны и
менять пароль подписи можно безболезненно.

**`APP_TZ` по умолчанию красноярский.** Если центр в другом регионе — поменяйте
сразу, иначе отложенные посты уедут на несколько часов.

**Значения с пробелами нужно брать в кавычки:** файл читает systemd, а он
`BREVO_SENDER_NAME=Молодёжный центр` разберёт не так, как вы ожидаете. Пишите
`BREVO_SENDER_NAME="Молодёжный центр"`.

### Шаг 4. Заполнить настройки фронтенда

```bash
sudo -u mediahub cp frontend/.env.example frontend/.env
sudo -u mediahub nano frontend/.env
```

```ini
BACKEND_URL=https://ваш.домен
NEXT_PUBLIC_YANDEX_MAPS_KEY=...
```

`BACKEND_URL` здесь обязателен, и без него сборка не пройдёт — специально:
раньше стояло умолчание, и фронтенд на чужом сервере молча работал с чужим
бэкендом. Такое замечают далеко не сразу.

Не путайте с одноимённой переменной в `backend/.env`: там это адрес, по
которому приложение при случае забирает собственные файлы, здесь — адрес, куда
интерфейс проксирует запросы. На одном сервере значение совпадает.

### Шаг 5. Служба и веб-сервер

```bash
sudo cp deploy/mediahub-backend.service /etc/systemd/system/
sudo cp deploy/mediahub-frontend.service /etc/systemd/system/
sudo systemctl daemon-reload

sudo cp deploy/nginx-mediahub.conf /etc/nginx/sites-available/mediahub
sudo sed -i 's/mediahub.example.ru/ваш.домен/g' /etc/nginx/sites-available/mediahub
sudo ln -sf /etc/nginx/sites-available/mediahub /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

### Шаг 6. Сертификат

```bash
sudo apt-get install -y certbot python3-certbot-nginx
sudo certbot --nginx -d ваш.домен
```

Certbot сам допишет строки сертификата в конфиг и настроит продление.

### Шаг 7. Запустить

```bash
sudo systemctl enable mediahub-backend mediahub-frontend
sudo bash deploy/update.sh --local
```

`update.sh` собирает интерфейс, применяет схему базы, перезапускает службы и
проверяет, что всё поднялось. Если что-то падает — он останавливается **до**
того, как тронет работающую версию, и говорит, где смотреть.

## 4. Первый вход

Свежая установка создаёт демонстрационных пользователей:
`admin@mediahub.ru` / `admin123!`.

**Смените пароль сразу после входа.** Это открытые в исходниках учётные данные.

Если хотите сделать администратором свою учётную запись, зарегистрируйтесь
обычным способом, а затем один раз добавьте в `backend/.env`:

```ini
BOOTSTRAP_ADMIN_EMAIL=вы@ваша.почта
```

и перезапустите бэкенд. После входа строку из файла уберите — она нужна
ровно один раз.

## 5. Проверить, что всё работает

```bash
curl -s https://ваш.домен/api/health | python3 -m json.tool
```

Ожидаемое:

```json
{
  "status": "ok",
  "database": { "ok": true },
  "schema": { "ok": true, "message": "схема на последней ревизии (...)" },
  "loops": {
    "scheduler":      { "ok": true },
    "publish_worker": { "ok": true },
    "retention":      { "ok": true },
    "telegram_stats": { "ok": true }
  }
}
```

`status: ok` и HTTP 200 — всё в порядке. При `degraded` приходит 503, и по
разделам видно, что именно сломалось. Эту же ссылку можно отдать любому
внешнему мониторингу: авторизации она не требует, наружу отдаёт только флаги и
счётчики.

Дальше стоит пройти сценарий целиком: создать пост, приложить фотографию,
опубликовать в подключённое сообщество и убедиться, что картинка на месте.
Именно на медиа вылезают ошибки с правами на каталог загрузок.

## 6. Обновление

```bash
cd /srv/mediahub && sudo bash deploy/update.sh
```

Порядок внутри выбран так, чтобы неудача не оставляла сайт лежащим: сначала
код и зависимости, потом **сборка**, потом миграции, и только затем
перезапуск. Упавшая сборка означает, что старая версия продолжает работать и
ничего не тронуто.

## 7. Резервные копии

```bash
sudo bash deploy/backup.sh
```

Кладёт в `/var/lib/mediahub/backups` сжатый дамп базы и архив загрузок, старше
двух недель удаляет. В ежедневный запуск:

```bash
sudo crontab -e
# 0 3 * * * /srv/mediahub/deploy/backup.sh >> /var/log/mediahub-backup.log 2>&1
```

**Копия на том же диске спасает от ошибки человека, но не от потери сервера.**
Настройте отправку каталога наружу — на другой сервер, в объектное хранилище,
куда угодно, лишь бы не сюда же.

Восстановление:

```bash
sudo systemctl stop mediahub-backend mediahub-frontend
gunzip -c /var/lib/mediahub/backups/db-ГГГГ-ММ-ДД_ЧЧММ.sql.gz \
  | sudo -u mediahub psql "$DATABASE_URL"
sudo tar -xzf /var/lib/mediahub/backups/uploads-ГГГГ-ММ-ДД_ЧЧММ.tar.gz -C /var/lib/mediahub/
sudo systemctl start mediahub-backend mediahub-frontend
```

Дамп сделан с `--clean`, поэтому накатывается поверх существующей базы.

## 8. Если что-то не так

Первым делом — логи. Они подробные и по-русски:

```bash
sudo journalctl -u mediahub-backend -n 100 --no-pager
sudo journalctl -u mediahub-frontend -n 100 --no-pager
```

У каждого обращения есть идентификатор, он же приходит в заголовке
`X-Request-Id` и в теле пятисотки. Если пользователь назвал этот номер —
запись находится точным поиском:

```bash
sudo journalctl -u mediahub-backend | grep 'НОМЕР'
```

### Частые случаи

**Бэкенд не поднимается, в логе «схема отстаёт».** Так и задумано: работать на
неполной схеме значит выдавать людям ошибки вместо честного отказа. Примените
миграции: `sudo bash deploy/update.sh --local`.

**Регистрация отвечает «BREVO_API_KEY не задан».** Почта не настроена.
Заполните `BREVO_API_KEY` либо блок `SMTP_*` и перезапустите бэкенд.

**Пост опубликовался, но без фотографий.** Почти всегда дело в `UPLOAD_DIR`:
приложение ищет файл не там, куда его положило. Проверьте, что значение в
`backend/.env` совпадает с каталогом, где файлы лежат на самом деле, и что у
пользователя `mediahub` есть к нему доступ:

```bash
ls -la /var/lib/mediahub/uploads | head
sudo journalctl -u mediahub-backend | grep 'загрузки:'
```

В логе при старте приложение печатает, где оно ищет файлы и сколько их видит.

**Файлы не загружаются, ошибка 413.** Слишком большой файл для nginx.
Поднимите `client_max_body_size` в конфиге и перезагрузите nginx.

**Отложенные посты не выходят.** Посмотрите `loops` в `/api/health`: если
`scheduler.ok` равен `false`, цикл встал — перезапустите бэкенд и загляните в
логи. Если циклы живы, проверьте `overdue_posts`: больше нуля означает, что
посты созрели, но не публикуются.

**После смены `JWT_SECRET` отвалились ВК и Telegram.** Из него выводился ключ
шифрования сохранённых токенов. Вернуть старое значение или переподключить
интеграции заново. Чтобы это не повторилось, задайте отдельный
`TOKEN_ENCRYPTION_KEY`.

**Интерфейс показывает чужие данные.** Значит `BACKEND_URL` во
`frontend/.env` не задан или указывает не туда. Проверьте и пересоберите.

## 10. Что дальше

Несколько вещей, которых в базовой установке нет и которые стоит сделать,
когда система приживётся:

- **Отдать копии наружу.** Самое важное из этого списка.
- **Мониторинг.** `/api/health` понимает любой аптайм-чекер; настройте
  оповещение на 503, иначе о вставшем планировщике вы узнаете от людей.
- **Файрвол.** `ufw allow 22,80,443/tcp` и запретить остальное. Порты 8000 и
  3000 наружу не нужны — службы и так слушают только localhost.
- **Ограничить SSH.** Вход по ключу, пароли отключить.
